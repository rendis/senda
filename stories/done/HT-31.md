# HT-31: Dashboard + Métricas

## Objetivo
Implementar la pantalla Dashboard (home) con métricas, gráficos, actividad reciente y tabla de emails recientes. El contenido se adapta al scope activo (Global/Tenant/Workspace).

## Entregables

1. **Dashboard layout**
   - Leer via Pencil MCP el frame "Screen/Dashboard" (Layer 2)
   - Grid: 4 metric cards arriba, chart + activity en medio, recent emails abajo

2. **Metric Cards**
   - Usar Component/MetricCard del Design System (leer via MCP)
   - Métricas: Total Emails Hoy, Delivery Rate, Bounce Rate, Complaint Rate
   - Fetch via TanStack Query: `GET /api/v1/manage/{scope}/metrics`

3. **Chart (emails últimos 7/30 días)**
   - Line chart con Recharts o similar (via shadcn/ui charts)
   - Toggle 7d / 30d
   - Datos desde API de métricas

4. **Activity Feed**
   - Lista de últimas acciones (audit log simplificado)
   - Scroll con límite de 10 items

5. **Recent Emails Table**
   - Mini-tabla con 4-5 rows
   - Columnas: destinatario, template, status badge, fecha
   - Link "View all" → /emails

6. **Scope-aware**
   - Global: top 5 tenants, alertas globales
   - Tenant: top 5 workspaces del tenant
   - Workspace: drafts pendientes, alertas del ws

## Reutilización

**Componentes que reutiliza de HT-28:**
- `PageShell` — layout principal con sidebar y header
- `EmptyState` — cuando no hay datos (ej. primer uso sin emails)
- `StatusBadge` — en tabla de recent emails y metric indicators

**Componentes nuevos a extraer:**
- `MetricCard` — card individual de métrica con número, label, y trending indicator
- `TimeRangeSelector` — toggle 7d/30d reutilizable
- `ActivityFeed` — lista scrollable de eventos recientes

## Metodología

Feature-first: Dashboard es la landing page post-login con vista agregada. Reutiliza `PageShell` para layout, `EmptyState` para primeros usos, y `StatusBadge` para estados visuales. Extrae `MetricCard`, `TimeRangeSelector`, y `ActivityFeed` como componentes de propósito general para reutilización en otras HTs o expansiones futuras.

## Criterios de Aceptación

- [ ] Dashboard renderiza con datos reales del API
- [ ] Metric cards muestran datos del scope actual
- [ ] Chart muestra datos de 7d/30d toggle
- [ ] Recent emails con status badges del Design System
- [ ] Responsive: mobile colapsa a stack vertical
- [ ] Diseño matchea frame de Pencil (via MCP)

## Definition of Done (DoD)

Cada feature se considera terminada SOLO cuando cumple estos 3 gates:

### Gate 1: Validación Visual (Pixel-Perfect)
1. Levantar la app en dev (`pnpm --dir web dev`)
2. Navegar a la pantalla implementada
3. Tomar screenshot via herramienta (o manualmente)
4. Leer el frame correspondiente del diseño via Pencil MCP
5. Comparar screenshot vs diseño de Pencil lado a lado
6. Verificar:
   - [ ] Layout y espaciado coinciden
   - [ ] Colores y tipografía correctos
   - [ ] Componentes del Design System usados (no custom)
   - [ ] Responsive: verificar en 1440px, 1024px, 768px
   - [ ] Empty states coinciden con diseño
   - [ ] Dark/light mode si aplica
7. Si hay drift visual → corregir en código, NO en Pencil

### Gate 2: Integración con Backend
1. Conectar contra backend real (docker-compose up)
2. Verificar cada endpoint que la feature consume:
   - [ ] GET lista carga datos reales
   - [ ] POST/PUT crea/edita correctamente
   - [ ] DELETE (soft) funciona con confirmación
   - [ ] Errores del backend se muestran correctamente (toast + mensaje)
   - [ ] Loading states mientras espera respuesta
   - [ ] Paginación cursor-based funciona
   - [ ] Filtros y búsqueda funcionan
3. Verificar auth:
   - [ ] Sin token → redirect a login
   - [ ] Token expirado → refresh o redirect
   - [ ] Rol insuficiente → mensaje de error, no crash

### Gate 3: Funcionalidad Completa
1. Todos los criterios de aceptación de la HT cumplidos
2. Componentes reutilizados del Design System (no duplicados)
3. Nuevos componentes extraídos a `components/shared/` si aplican
4. Zero errores en console del browser
5. Zero warnings de TypeScript
6. `pnpm --dir web lint` pasa
7. `pnpm --dir web typecheck` pasa sin errores
