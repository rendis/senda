### 2. Flujos Happy Path (éxito completo)

Cada flujo se ejecuta end-to-end: HTTP request → procesamiento → base de datos → workers → email → webhook.

- **F01: Onboarding completo** — primer login OIDC → crear tenant → crear workspace → superadmin asignado
- **F02: Setup workspace** — crear injectors → crear adapter (SES) → test connection via Mailpit → registrar dominio → verificar dominio
- **F03: Template lifecycle** — crear template type → crear template → editar draft → agregar locales → publicar → archivar → crear nueva versión → publicar
- **F04: Envío exitoso** — POST /send con template válido → 202 Accepted → River procesa → MJML compila → DKIM firma → email enviado a Mailpit → estado `delivered` → webhook disparado
- **F05: Envío batch** — POST /send con 50 destinatarios → 50 tracking_ids → todos procesados → estados correctos
- **F06: Consulta por external_id** — enviar 5 emails con mismo external_id → GET /emails?external_id=X → 5 resultados cross-workspace
- **F07: Herencia completa** — definir template global → override en _system → override en workspace → enviar → verificar que se usó el del workspace
- **F08: Injector merge** — definir injector global (3 campos) → override 1 campo en workspace → enviar → verificar merge correcto (2 campos globales + 1 override)
- **F09: API Key lifecycle** — crear key → enviar email con key → revocar → intentar enviar → 401
- **F10: Member roles** — crear miembros con distintos roles → verificar acceso a cada endpoint según rol

### 3. Flujos de Fallo Controlado (errores esperados)

- **E01: Template desactivado** — desactivar template → POST /send → 409 Conflict con mensaje claro
- **E02: Sin adapter configurado** — workspace sin adapter en cadena → POST /send → 422 con mensaje descriptivo
- **E03: Dominio no verificado** — from_email con dominio sin verificar → POST /send → 422
- **E04: Rate limit excedido** — enviar ráfaga sobre el límite → 429 Too Many Requests con Retry-After
- **E05: Variables inválidas** — POST /send con variables que no matchean el schema del template type → 400
- **E06: Tenant/workspace no existe** — POST /send con códigos inexistentes → 404
- **E07: API Key de otro workspace** — API Key de ws-A intenta operar en ws-B → 403
- **E08: Editor intenta publicar** — workspace-editor intenta publicar template → 403
- **E09: Viewer intenta escribir** — workspace-viewer intenta crear template → 403
- **E10: Duplicate codes** — crear tenant con código duplicado → 409
- **E11: Email suprimido** — agregar email a suppression list → enviar → estado `suppressed`, email NO enviado
- **E12: Soft delete + purge** — soft delete template → verificar dependencias → confirmar purge → verificar cascade

### 4. Flujos de Fallo Forzado (chaos testing)

- **C01: Provider caído** — Mailpit down durante envío → River reintenta → verificar backoff exponencial
- **C02: DB connection lost** — matar PG durante request → recovery graceful → logs correctos
- **C03: Worker crash** — matar River worker con jobs en queue → restart → jobs retomados sin pérdida
- **C04: Race condition envío** — 100 requests concurrentes al mismo template → no corrupción, no duplicados
- **C05: Race condition publicar** — 2 admins publican versiones distintas simultáneamente → solo 1 gana, estado consistente
- **C06: Rate limiter bajo carga** — 1000 requests/seg → token bucket funciona correctamente → no leak
- **C07: Webhook endpoint lento** — webhook target con 10s delay → timeout handled → consecutive_failures incrementa → auto-disable
- **C08: Payload gigante** — POST /send con body de 10MB → 413 o 400, no crash
- **C09: Cache invalidation race** — modificar template + enviar simultáneamente → cache invalidada → versión correcta usada

### 5. Pentesting OWASP (seguridad)

Basado en `docs/specs/SECURITY_CHECKLIST.md`:

- **S01: Injection** — SQL injection en filtros de búsqueda, template variables, injector values
- **S02: Broken Auth** — tokens expirados, tokens manipulados, OIDC bypass attempts
- **S03: Broken Access Control** — escalación horizontal (ws-A accede datos de ws-B), escalación vertical (editor intenta admin)
- **S04: XSS via templates** — inyectar `<script>` en template body, subject, preview text → verificar sanitización
- **S05: SSRF via webhooks** — webhook URL apuntando a localhost, metadata endpoints (169.254.169.254)
- **S06: Mass assignment** — enviar campos extra en JSON (role, is_admin, tenant_id) → ignorados
- **S07: IDOR** — acceder recursos por UUID de otro tenant/workspace sin autorización
- **S08: Rate limit bypass** — rotar headers, IPs simuladas → rate limit persiste
- **S09: API Key timing attack** — medir tiempo de respuesta con keys parcialmente correctas → timing constante
- **S10: Cryptographic validation** — DKIM signatures verificables, AES-256-GCM encrypt/decrypt ciclo completo
- **S11: Header injection** — inyectar headers SMTP via from_name, subject → sanitizado
- **S12: Path traversal** — template slugs con `../`, `%2e%2e` → rechazados

### 6. Colección Postman (`docs/postman/`)

Documentar TODOS los endpoints en una colección Postman profesional:

```
docs/postman/
├── senda-api-v1.postman_collection.json
├── senda-local.postman_environment.json
├── senda-staging.postman_environment.json
└── README.md
```

**Requisitos de la colección:**

- **Organización por carpetas:** Auth, Onboarding, Tenants, Workspaces, Members, Injectors, Template Types, Templates, Adapters, Domains, Emails, Webhooks, API Keys, Audit Log, Settings, Health
- **Cada request debe tener:**
  - Nombre descriptivo (ej: "Create Template Type — welcome-email")
  - Descripción en markdown (qué hace, cuándo usarlo, qué rol necesita)
  - Headers correctos (Authorization, Content-Type)
  - Body de ejemplo con datos realistas
  - Variables de entorno (`{{base_url}}`, `{{token}}`, `{{tenant_code}}`, `{{workspace_code}}`)
  - Tests de Postman (assertions de status code, schema, campos clave)
  - Pre-request scripts para auth token refresh
- **Flujos documentados como "Runner":**
  - Onboarding flow (3 pasos)
  - Template creation flow (type → template → version → publish)
  - Send email flow (send → query → track)
- **Variables de entorno:**
  - `base_url`: `http://localhost:8080/api/v1`
  - `oidc_token`: placeholder para JWT
  - `api_key`: placeholder para API Key
  - `tenant_code`: `test-corp`
  - `workspace_code`: `main`

## Reglas para el Team QA

1. **Mentalidad adversarial** — tu trabajo es romper el sistema, no confirmar que funciona
2. **Cada bug encontrado** → se documenta como issue con: pasos para reproducir, expected vs actual, severidad
3. **No marques esta HT como done** si hay bugs críticos o altos abiertos
4. **Regression suite** — todos los tests deben ser re-ejecutables (`make test-e2e`)
5. **Los tests son código** — mismos estándares de calidad que el código de producción
6. **Mailpit es tu mejor amigo** — verificar headers, body, DKIM, destinatarios, todo via API REST
